## What this page does

These guides connect the framework's individual strategies into inspectable
workflows. They begin with the conservative dense-equivalence baseline, add the
complete packaged anchored top-1 lifecycle, and then introduce explicitly
composed weighted top-2 execution, adaptive route selection, always-on-anchor
deltas, package-local two-expert training, and hierarchical package routing.
Prompt-level shortlisting then shows how an external retrieval stage can bound
the columns evaluated by token-level routing.

The comparison table keeps integration boundaries visible from the start.
Exact conversion, packaged top-1, weighted top-2, adaptive selection, routed
LoRA deltas, local mini-MoE training, package-first hierarchy, and
prompt-shortlisted top-1 are published below. The final guide adds a global
top-2 policy that rejects cross-group pairs before sparse execution.

## Exact anchor conversion

<IntegrationBadge status="Integrated" />

### The problem it solves

Before adding specialists, conversion must prove that wrapping selected dense
MLPs does not change the model. This workflow creates a tiny local Qwen3 model,
records its outputs, converts the upper-half MLPs to routed wrappers, and
compares the result with zero tolerance.

### Workflow contract

- **Expert representation:** none; the original dense MLP remains candidate
  zero.
- **Routing and selection:** every converted wrapper starts in
  `forced_anchor`, so no router score is evaluated.
- **Combination and capacity:** the anchor output is returned directly;
  specialist mixing and overflow handling are inactive.
- **Training and calibration:** neither is required.
- **Active work:** one anchor MLP per token at every converted layer.
- **Packaging and serialization:** no expert package is created. The example
  validates conversion before package lifecycle work begins.
- **Expected result:** every hidden state and final logit is exactly equal on
  the deterministic CPU fixture.

### How it runs

```text
Tiny local Qwen3 anchor
  → record dense hidden states and logits
  → wrap upper-half MLPs in forced-anchor mode
  → execute the same input
  → require exact tensor equality
```

The wrapper retains the same original MLP object as `anchor_mlp`. The
integration test also fingerprints its parameters before conversion and
requires that fingerprint to remain unchanged.

## Packaged anchored top-1

<IntegrationBadge status="Integrated" />

### The problem it solves

Exact conversion establishes a safe anchor but does not yet specialize the
model. This workflow trains a full-MLP code expert without changing the anchor,
fits and calibrates an independent router head, derives an immutable routed
package, explicitly synchronizes that package into the model, and saves a
composition that reloads with the same routed behavior.

This is the primary integrated workflow because every stage is available
through package APIs. The offline verification scripts exercise the stages
independently with deterministic temporary fixtures; they do not pass a
persistent artifact from one script to the next.

### Workflow contract

- **Expert representation:** one full copied-MLP expert, `code:0`, for each
  converted layer.
- **Training:** forced-path training sends every training token through the new
  expert while mechanically freezing the anchor and shared model.
- **Router:** one append-only affine head per `(layer, expert)` binding, fitted
  with ridge regression and calibrated with held-out temperature and threshold
  rows.
- **Selection:** anchored hard top-1 compares the calibrated specialist score
  with the anchor's permanent score of zero.
- **Combination and capacity:** exactly one complete path runs per token. A
  positive winning specialist runs alone; otherwise the anchor runs alone.
- **Packaging:** expert tensors, router heads, calibration provenance, hashes,
  and explicit layer bindings form an immutable package.
- **Lifecycle:** install, unload, and reinsert update the registry only.
  `synchronize_registry()` is the explicit boundary that changes model
  execution.
- **Serialization:** the composition bundles active package bytes and references
  the external anchor checkpoint instead of duplicating its weights.
- **Expected result:** reload restores the same registry identity and exactly
  the same routed logits on the deterministic CPU fixture.

### How it runs

```text
Frozen Qwen3 anchor
  → train full-MLP experts through forced paths
  → export an immutable expert-only package
  → fit and calibrate independent affine router heads
  → derive an immutable routed package
  → install, then explicitly synchronize anchored top-1
  → save and reload the composition
  → require exact routed-logit and registry restoration
```

Installation and synchronization are deliberately separate. This prevents a
registry mutation from silently changing live model behavior and keeps router
recalibration an explicit operation.

### Current limitations

- The examples use tiny deterministic Qwen3 fixtures and synthetic data. They
  validate framework behavior, not code-specialization quality.
- Qwen3 is the only validated model-family backend.
- Full-MLP experts duplicate each converted MLP. Package-driven LoRA
  materialization remains separate future work.
- The composition references a compatible external anchor checkpoint; it does
  not bundle the anchor weights.
- The exact reload claim applies to the validated CPU path. Reduced precision,
  optimized kernels, multi-device execution, and distributed execution need
  separate validation.
- Installing or removing a package does not change live execution until
  synchronization is requested. Router recalibration is never automatic.
- The offline scripts validate consecutive lifecycle stages independently
  rather than acting as a persistent multi-process pipeline.

## Weighted top-2 specialists

<IntegrationBadge status="Composable" />

### The problem it solves

Anchored top-1 cannot combine two specialists whose transformations may be
useful together. This workflow ranks the fixed-zero anchor beside two affine
specialist scores, approves a pair only when both specialist scores are
strictly positive, executes the selected experts sparsely, and mixes their
activations with score-softmax weights.

The selection, combination, capacity, and dispatch parts are validated through
public APIs, but they require explicit assembly. Package synchronization does
not attach this strategy to `RoutedMLP`, and `AnchoredMoEConfig` does not accept
top-2 as a model-level policy.

### Workflow contract

- **Expert representation:** two compatible complete experts. The verified
  dispatch example uses frozen full-MLP experts derived from the same anchor.
- **Router:** append-only affine heads score identity features in stable expert
  order.
- **Selection:** anchor-veto top-2 ranks the permanent zero-score anchor with
  every specialist. The specialist pair runs only when both winning specialist
  scores are strictly positive.
- **Combination:** score-softmax converts the ordered specialist scores into
  non-negative weights that sum to one.
- **Capacity:** explicit per-token availability is applied only after a pair is
  approved. Both available experts run as top-2; one survivor runs alone with
  weight `[1, 0]`; no survivors return to the anchor.
- **Training and calibration:** this example consumes already constructed
  experts and affine scores. It does not train experts, fit heads, or establish
  that the selected mixture improves quality.
- **Active work:** an anchor token executes one MLP, a capacity-degraded token
  executes one specialist MLP, and an effective top-2 token executes two
  specialist MLPs.
- **Packaging and serialization:** standalone objects are assembled directly.
  Package-driven top-2 attachment and composition reload are not implemented.
- **Expected result:** no token is dropped, inactive experts do not execute,
  original token order is restored, and every effective pair has finite
  sum-to-one weights.

### How it runs

```text
Hidden states
  → append-only affine scores
  → rank [anchor = 0, specialist scores]
  → anchor veto unless two specialists are positive
  → apply explicit expert availability
  → sparsely execute zero, one, or two specialists
  → score-softmax effective pairs
  → reconstruct the original token order
```

Selection and capacity answer different questions. Anchor veto decides whether
the evidence supports a specialist pair. Capacity handling then decides how
much of that already-approved pair is currently available; it never searches
for a replacement expert outside the selected pair.

### Selection and mixture rule

## Adaptive anchor/top-1/top-2

<IntegrationBadge status="Composable" />

### The problem it solves

Fixed top-1 always spends one MLP execution, while anchor-veto top-2 requires
two positive specialists before either one can run. Adaptive selection keeps
the anchor when specialist evidence is absent, runs one specialist when only
the strongest score is convincing, and approves a pair when the second score
clears a separate mixture threshold.

This makes the intended computation visible per token without forcing every
specialist-routed token to pay for a second expert. The selection policy and
its affine-router integration are validated through public APIs. Replacement
expert execution still requires an explicit dispatcher that does not yet
accept adaptive decisions.

### Workflow contract

- **Expert representation:** zero, one, or two compatible complete experts may
  be selected. The verified fixture exercises route metadata rather than
  expert activations.
- **Router:** append-only affine heads score frozen identity features in stable
  expert order.
- **Selection:** the best specialist must be strictly positive to beat the
  fixed-zero anchor. A second specialist joins only when its score is strictly
  greater than `mix_threshold`; an exact threshold tie remains top-1.
- **Combination and capacity:** the decision records ranked candidates and
  route arity, but the fixture does not execute or combine replacement
  experts. No serving-capacity degradation is applied.
- **Training and calibration:** the example consumes deterministic affine
  heads. It does not train experts, fit router weights, or calibrate the
  mixture threshold.
- **Active work:** route arity zero means one anchor MLP execution; arity one
  means one specialist MLP execution; arity two means two specialist MLP
  executions. The evaluation utilities validate this accounting separately.
- **Packaging and serialization:** standalone objects are assembled directly.
  Adaptive package attachment, model-level configuration, and composition
  reload are not implemented.
- **Expected result:** the four tokens deterministically choose top-2, top-1,
  anchor, and top-1, including the exact-threshold boundary case.

### How it decides

```text
Calibrated specialist scores
  → no positive winner: anchor
  → one positive winner, second score at or below threshold: top-1
  → second score strictly above threshold: top-2
  → retain ranked candidates, masks, and route arity for auditing
```

The activation threshold and mixture threshold answer different questions.
Zero asks whether any specialist should replace the anchor. `mix_threshold`
asks whether the runner-up provides enough evidence to justify a second
specialist execution.

## Always-on anchor with routed LoRA deltas

<IntegrationBadge status="Composable" />

### The problem it solves

Replacement routing chooses the anchor or a specialist. This workflow instead
keeps the immutable anchor active for every token and adds zero, one, or two
selected anchor-relative LoRA updates. Tokens with no useful specialist
evidence therefore preserve the dense output exactly, while positive routes
can adapt it without replacing the anchor path.

The delta expert, adaptive selection, availability fallback, sparse dispatch,
combination, and explicit `RoutedMLP` mode are validated through public APIs.
They still require direct assembly: installed packages do not automatically
materialize LoRA experts or activate this execution mode.

### Workflow contract

- **Expert representation:** each `PEFTLoRAExpert` owns adapter tensors over a
  frozen private copy of the compatible anchor MLP. Its `forward_delta()` path
  returns the complete private-expert output minus the already-computed live
  anchor activation.
- **Router:** the verified fixture supplies deterministic scores for `code`
  and `math` in stable expert order. A separate tiny-Qwen3 integration test
  binds the same delta runtime to an identity feature extractor and frozen
  affine head.
- **Selection:** adaptive selection chooses zero, one, or two specialists.
  The fixed-zero anchor wins when the best score is non-positive; the runner-up
  joins only when it is strictly above `mix_threshold`.
- **Combination and capacity:** unavailable selected experts are removed
  without searching outside the selected set. Zero survivors return the exact
  anchor, one survivor receives unit weight, and two survivors receive
  score-softmax weights.
- **Training and calibration:** the guide starts from deterministic standalone
  adapters and scores. It does not train LoRA factors, fit router heads,
  calibrate thresholds, or prove that a selected mixture improves quality.
- **Active work:** the anchor executes once for every token, followed by zero,
  one, or two sparse delta-expert calls. The current LoRA delta path computes a
  complete private expert before subtraction, so this is a correctness
  reference rather than a native delta-only performance kernel.
- **Packaging and serialization:** explicit `RoutedMLP` configuration is
  available, and standalone LoRA adapter payloads are validated. Package-driven
  LoRA materialization and composition-checkpoint reload are not implemented.
- **Expected result:** three tokens take exact anchor, top-1 delta, and top-2
  delta routes; the anchor row is bitwise equal, active weights follow route
  arity, and the live anchor remains frozen.

### How it runs

```text
Live immutable anchor → execute every token once
Deterministic specialist scores → adaptive zero/top-1/top-2 selection
Explicit availability → keep selected survivors or return to anchor
Sparse LoRA delta calls → zero, unit, or score-softmax weights
Anchor activation + weighted deltas → final output and auditable route data
```

The anchor and delta branches have different responsibilities. The anchor is
the stable base computation, while each selected specialist contributes only
its change relative to that base.

## Two-expert local mini-MoE training

<IntegrationBadge status="Composable" />

### The problem it solves

Independently trained experts can each be useful while still combining poorly.
This workflow trains exactly two package-local experts and fresh affine router
heads together, allowing their transformations and mixture weights to
co-adapt without changing the anchor or shared backbone.

There are two supported entry points. `TRN-003` starts the local pair directly
from compatible expert objects. `TRN-004` first trains the same pair
independently through `TRN-002`, then applies the identical joint local
runtime as a mixture-aware refinement stage. Both paths are composable
training workflows rather than package-driven deployment paths.

### Workflow contract

- **Expert representation:** exactly two complete experts cover the same
  converted layers in the same stable order. The verified examples use
  full-MLP experts copied from the immutable anchor.
- **Router:** fresh zero-initialized affine heads are owned by the local pair.
  Small opposite biases break the symmetry between anchor-copied experts
  deterministically before optimization begins.
- **Selection and combination:** no sparse top-1 decision occurs during local
  training. Both experts execute every specialization token, and COM-001
  score-softmax weights mix their activations.
- **Training:** ordinary Hugging Face `Trainer` optimization updates only the
  expert-declared parameter subsets and local affine heads. The anchor,
  backbone, feature extractor, and incumbent artifacts remain frozen.
- **Optional balancing:** BAL-003 adds a Switch-style auxiliary objective from
  local mixture probabilities. It changes training pressure but not execution;
  both experts still run for every eligible token.
- **Active work:** two specialist MLPs per specialization token at every
  converted layer. There is no anchor abstention, capacity overflow, or token
  dropping inside this dense local training path.
- **Lifecycle cleanup:** success and failure both clear gradients, freeze the
  local artifacts, release retained objective observations, and restore every
  converted wrapper to exact `forced_anchor` execution.
- **Packaging and serialization:** training reports record immutable topology,
  optimizer ownership, progress, and final objectives. Packaging the trained
  local router with its expert pair and attaching it for inference remain
  future work.
- **Expected result:** both experts and router heads train, the anchor remains
  byte-exact, and no local training route remains attached after the run.

### How the two paths run

```text
Direct local training (TRN-003)
  compatible two-expert rectangle + fresh heads
  → validate ownership and storage isolation
  → jointly train dense score-softmax mixtures
  → freeze artifacts and restore forced anchor

Mixture-aware refinement (TRN-004)
  train the same two experts independently (TRN-002)
  → verify report order and layer topology
  → run the unchanged TRN-003 joint stage
  → return one immutable report linking both stages
```

The refinement coordinator does not infer historical identity from mutable
objects. It requires the caller-owned bindings to match the completed
independent report's stable expert order and complete layer rectangle before
it attaches the local route.

## Hierarchical package routing

<IntegrationBadge status="Research primitive" />

### The problem it solves

A flat router must compare every specialist for every token, even when
specialists already belong to distinct packages such as code and mathematics.
This workflow first asks whether any package has positive evidence over the
anchor. Only the winning package then scores its local experts and contributes
a pair, keeping every mixture inside one package.

The hierarchy is useful for studying larger expert collections without
pretending that package-level and local scores form one globally calibrated
score bank.

### Workflow contract

- **Expert representation:** two or more globally unique, package-local expert
  IDs per package. The verified sparse execution fixture uses four deterministic
  complete expert modules across two packages.
- **Routing and selection:** anchored package top-1 runs first. Selected
  non-anchor rows are grouped by package and scored only by that package's
  frozen local logical router. Stable local top-2 then selects a pair without a
  second anchor veto.
- **Combination and capacity:** `AnchoredTop2Dispatcher.dispatch_preselected()`
  reuses the ordinary top-2 validation, sparse execution, score-softmax
  combination, and reconstruction path. Capacity policies remain independently
  composable.
- **Training and calibration:** this workflow assumes that package and local
  affine heads already exist. It performs no fitting, calibration, or hidden
  recalibration.
- **Active work:** every token receives package scores. An anchor token runs one
  anchor MLP and receives no local scores; an approved token receives only its
  winning package's local scores and runs that package's selected expert pair.
- **Packaging and serialization:** the hierarchy is assembled explicitly in
  memory from copied, frozen logical routers. There is no hierarchy manifest,
  package-driven model attachment, or hierarchy checkpoint format.
- **Expected result:** package selection is anchor-first, local scoring omits
  anchor rows, selected pairs never cross package boundaries, and sparse
  execution restores the original token order.

### How the two stages run

```text
Token features
  → score every package against the fixed-zero anchor
  → anchor rows stop at the dense MLP
  → group approved rows by their winning package
  → score only that package's local experts
  → select the package-local top two
  → reuse sparse top-2 dispatch and score-softmax combination
```

Package ties follow stable package order after the anchor-first comparison.
Once a package wins, its local pair is unconditional: negative local scores
remain eligible because the package gate already made the abstention decision.

## Prompt-shortlisted token routing

<IntegrationBadge status="Research primitive" />

### The problem it solves

A flat logical router evaluates every installed expert column for every token.
That remains reasonable for a small registry, but its scoring and expert-memory
overhead grows with the complete candidate set. This workflow uses external
prompt-level evidence to retain at most \(M\) candidates before ordinary
token-level routing.

Shortlisting bounds which affine columns are evaluated without weakening the
anchor. A shortlisted specialist still needs positive token-level evidence;
otherwise anchored top-1 returns the token to the dense MLP.

### Workflow contract

- **Expert representation:** any complete experts that already satisfy the
  selected token-routing and dispatch contracts. The deterministic fixture
  uses code, mathematics, and science stand-ins.
- **Routing and selection:** `PromptTopMShortlister` consumes one finite
  retrieval score per prompt and candidate. `PromptShortlistedLogicalRouter`
  evaluates only the selected logical-router columns, reconstructs the stable
  global candidate order, and passes the resulting scores to `POL-001`
  anchored top-1.
- **Combination and capacity:** top-1 execution uses the selected complete
  expert directly. Anchor fallback and capacity remain the responsibility of
  the existing selection and dispatch path.
- **Training and calibration:** external retrieval scores and the frozen
  logical-router heads are inputs. This primitive does not train a prompt
  encoder, fit retrieval scores, recalibrate token heads, or mutate experts.
- **Active work:** prompt retrieval considers the caller-provided candidate
  table once. Token routing evaluates at most \(M\) affine expert columns per
  prompt row, then sparse dispatch runs either the anchor or one specialist per
  token.
- **Packaging and serialization:** the shortlist and copied logical-router
  wrapper are assembled explicitly in memory. They are not stored in an expert
  package, registry router version, or composition checkpoint.
- **Expected result:** prompt ties preserve candidate order, unselected columns
  are never evaluated, global expert identity remains stable, and shortlisted
  negative evidence still falls back exactly to the anchor.

### How the two routing scales compose

```text
External prompt retrieval scores
  → select at most M candidates for each prompt
  → evaluate only those token-router columns
  → restore the stable global expert score order
  → apply fixed-zero anchored top-1 per token
  → sparsely execute the winner or the anchor
```

The prompt stage limits eligibility; it does not choose the executing expert.
The token stage can abstain, but it cannot recover an expert omitted by the
prompt shortlist.

## Compatibility-constrained global top-2

<IntegrationBadge status="Research primitive" />

### The problem it solves

Ordinary global top-2 can combine the two highest-scoring specialists even
when they were trained independently and should never run as one mixture.
Compatibility-constrained top-2 keeps global candidate scoring, but permits a
pair only when both experts declare the same non-empty compatibility group.

The rule is conservative in two ways. Two positive scores are required, and a
missing group means “not mixable” rather than membership in an implicit
default group. When no eligible pair exists, the fixed-zero anchor vetoes
specialist execution.

### Workflow contract

- **Expert representation:** complete experts with stable IDs and explicit
  package payload bindings. Every expert considered at a converted layer must
  appear exactly once in the compatibility index.
- **Routing and selection:** calibrated scores retain global expert order.
  `CompatibilityConstrainedTop2Selection` evaluates distinct, positive,
  same-group pairs and ranks them lexicographically by their stronger and
  weaker member scores. Stable append order resolves exact ties.
- **Combination and capacity:** an eligible pair uses the existing
  score-softmax combination and `INF-002` sparse pair dispatcher. If no
  eligible pair exists, selection produces an anchor-containing decision and
  the dispatcher executes the dense anchor exactly.
- **Training and calibration:** the policy consumes frozen scores and declared
  metadata. It does not learn compatibility, recalibrate router heads, or
  change expert parameters.
- **Active work:** all \(K\) specialist scores remain inputs, compatibility
  filtering considers candidate pairs, and execution remains bounded to the
  anchor or two specialists per token.
- **Packaging and serialization:** `ExpertRegistry.mixture_compatibility()`
  derives an immutable layer-local index from active packages. Selection and
  dispatch are then assembled explicitly; they are not automatically attached
  to `RoutedMLP` or saved in a composition checkpoint.
- **Expected result:** higher-scoring incompatible or ungrouped specialists
  never execute, compatible selected pairs preserve score gradients and sparse
  calls, and registry changes produce a new exact index or anchor fallback.

### How compatibility filters global routing

```text
Active package manifests and payload bindings
  → derive a layer-local compatibility index
  → score specialists in stable global order
  → keep distinct positive pairs in one explicit group
  → choose the lexicographically strongest eligible pair
  → mix that pair, or execute the anchor exactly
```

Compatibility is an eligibility rule, not a second router. It prevents invalid
mixtures but does not reduce the number of router columns scored.

and the dispatcher executes only the anchor.

### Minimal explicit composition

```python
compatibility = registry.mixture_compatibility(layer_index=2)
dispatcher = AnchoredTop2Dispatcher(
    selection_policy=CompatibilityConstrainedTop2Selection(compatibility),
)
result = dispatcher.dispatch(
    hidden_states, expert_scores=scores,
    expert_ids=compatibility.expert_ids,
    anchor_mlp=anchor, experts=experts,
)
```

The registry supplies immutable compatibility metadata; the caller explicitly
connects it to the validated pair selection, combination, and dispatch path.

### Current limitations

- Compatibility requires explicit package payload bindings and complete,
  unambiguous layer coverage. Legacy binding-free packages cannot supply an
  index.
- A package-level group is a coarse permission. Version 1 does not learn
  pairwise utility, express layer-specific group membership, or prove that an
  allowed mixture is beneficial.
- Pair filtering does not reduce flat-router score work and a straightforward
  global pair search scales quadratically with the candidate count.
- The validated path is explicit standalone composition. Package-driven
  top-2 `RoutedMLP` attachment, model-level strategy configuration,
  composition-checkpoint persistence, and route telemetry remain future work.
- Capacity degradation beyond the existing pair-shaped dispatcher,
  accelerator performance, distributed execution, and production-scale
  registries are not validated here.
- The fixtures establish deterministic eligibility, lifecycle updates, sparse
  calls, gradients, and exact fallback—not specialization quality or gains
  from expert synergy.
